# راهنمای کار موازی دو توسعه‌دهنده

## اصل

موازی‌سازی بر اساس قابلیت و interface انجام می‌شود، نه تقسیم تصادفی صفحه‌ها. معماری modular monolith است: مرزها service-grade هستند، اما ماژول‌ها deployment یا database جدا ندارند.

## دو مسیر وب

### مسیر خریدار

- فروشگاه عمومی، کالا و فیدهای «دنبال‌شده‌ها» و «اکسپلور»
- سبد تک‌فروشگاهی و ثبت سفارش
- حساب خریدار و تجربه خرید
- پیگیری سفارش و پیگیری مشکلات از دید خریدار

### مسیر فروشنده

- راه‌اندازی و شخصی‌سازی فروشگاه
- کالا، قالب، گونه و موجودی
- سفارش، انجام سفارش و ارسال
- گفت‌وگو، گزارش پایه و پیگیری مشکلات از دید فروشنده

هر دو مسیر در یک برنامه Next.js قرار دارند، اما route group، پوشه و تست مستقل دارند. import مستقیم implementation مسیر دیگر یا قرار دادن منطق دامنه در React component و Server Action ممنوع است. هر دو مسیر client تولیدشده از OpenAPI را مصرف می‌کنند.

## ماژول‌های دامنه و مشترک

- هویت و دسترسی
- فروشگاه
- کالا
- موجودی
- سفارش
- پرداخت
- انجام سفارش
- گفت‌وگو
- پیگیری مشکلات
- محتوا
- فیدها و دنبال‌کردن
- رسانه
- اعلان‌ها
- گزارش و آمار

مالکیت دقیق و جهت وابستگی در [ADR-002](../architecture/decisions/002-module-boundaries-and-parallel-contracts.md) ثبت شده است.

## مالکیت موقت

- هر Issue یک مالک هماهنگی دارد و ماژول‌ها، interfaceها، جدول‌ها و migrationهای قابل تغییر را در توضیح خود اعلام می‌کند.
- هیچ فردی مالک دائمی یک ماژول نیست.
- در هر لحظه فقط یک شاخه interface یا migration یک ماژول را تغییر می‌دهد.
- انتقال مالکیت در Issue ثبت می‌شود، نه با توافق شفاهی یا حدس از نام پوشه.
- design system، تنظیمات سراسری و بسته مشترک نیز در هر لحظه یک مالک دارند.

## قرارداد پیش از مصرف

هر تغییر مشترک ابتدا یک قرارداد کوچک با واژگان، حالت‌ها، ورودی/خروجی، خطاها، مجوزها، رخدادها و معیار پذیرش دارد. مالک ماژول interface و نسخه آن را نگه می‌دارد؛ مصرف‌کننده contract test خود را اضافه می‌کند.

تغییر ناسازگار در سه مرحله انجام می‌شود:

1. افزودن نسخه یا فیلد جدید؛
2. مهاجرت همه مصرف‌کنندگان؛
3. حذف قرارداد قدیمی.

## داده و migration

- هر جدول دقیقاً یک ماژول مالک دارد.
- خواندن، join یا نوشتن مستقیم جدول ماژول دیگر ممنوع است.
- شناسه ماژول دیگر فقط مقدار مرجع است و رابطه ORM قابل پیمایش نیست.
- تغییر هم‌زمان دو مالک ابتدا به PR قرارداد کوچک شکسته می‌شود.
- گزارش و فیدها projectionهای خود را دارند و منبع حقیقت عملیات نیستند.

## ارتباط و گردش کار

- پاسخ لازم در همان کار: interface هم‌زمان.
- واکنش پس از ثبت واقعیت: رخداد outbox با تحویل حداقل یک‌بار و مصرف‌کننده idempotent.
- تماس provider خارجی داخل transaction پایگاه داده انجام نمی‌شود.
- use case چندماژولی یک گردش کار کوچک و بدون جدول دارد؛ orchestrator عمومی ساخته نمی‌شود.

## کنترل ادغام

- یک Issue و یک شاخه برای هر واحد کار؛
- PR کوچک قرارداد پیش از شاخه‌های مصرف‌کننده؛
- اعلام فایل‌های مشترک و اثر قرارداد در توضیح PR؛
- architecture test برای importها و مالکیت داده؛
- integration test هر ماژول با PostgreSQL واقعی؛
- compatibility و contract test برای OpenAPI و رخداد؛
- آزمون سرتاسری گردش کارهای چندماژولی؛
- fake قراردادی برای adapterهای خارجی؛
- rebase یا merge منظم از شاخه پایه و PRهای کوتاه‌عمر.
