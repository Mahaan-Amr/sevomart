# امکان‌پذیری سرویس‌های فنی لازم در ایران

تاریخ بررسی: ۲۰ مرداد ۱۴۰۵ (۱۱ اوت ۲۰۲۶)

## پاسخ کوتاه

برای درگاه پرداخت، تسویه بانکی، پیامک رمز یک‌بارمصرف، ثبت و رهگیری مرسوله و اعلان، سرویس‌های دارای مستندات رسمی در ایران وجود دارند. بااین‌حال، این پژوهش انتخاب نهایی ارائه‌دهنده را توجیه نمی‌کند:

- **تسویه مستقیم** از نظر فنی شدنی است، اما باید روشن شود هر فروشنده پذیرنده و دارنده درگاه مستقل است یا پلتفرم از یک کیف پول مرکزی به شباهای فروشندگان تسویه می‌کند. این دو مدل مسئولیت قراردادی و مالی متفاوت دارند.
- **پرداخت محافظت‌شده** نزدیک‌ترین تطابق عمومی را در «معاملات امن میاندو» وندار دارد؛ فعال‌سازی آن نیازمند تأیید ارائه‌دهنده است و اطلاعات هویتی نسبتاً زیادی از دو طرف می‌خواهد. وضعیت تولیدی فعلی، قواعد اختلاف، دسته‌های مجاز و قرارداد آن باید استعلام و با نمونه واقعی سنجیده شود.
- **OTP پیامکی** با دست‌کم دو API داخلی مستند شدنی است. تأیید الگوی پیام، کیفیت تحویل بین اپراتورها و رفتار در محدودیت پیامک تبلیغاتی نیازمند نمونه بار واقعی است.
- **ورود گوگل** از نظر فنی استاندارد و قابل پیاده‌سازی است، اما گوگل دسترس‌پذیری تجاری برخی خدمات خود در ایران را محدود می‌کند و سند اختصاصی روشنی که دسترس‌پذیری Google Identity Services را برای یک کسب‌وکار ایرانی تضمین کند پیدا نشد. بنابراین فقط مسیر اختیاری است و باید از چند شبکه و دستگاه داخل ایران آزمایش شود. شماره موبایل محلی همچنان پیش از اقدام حساس تأیید می‌شود.
- **رهگیری ارسال** با APIهای تجاری تیپاکس و چاپار قابل بررسی است؛ برای شرکت پست، رهگیری عمومی وجود دارد اما در این بررسی سند عمومی رسمی API برای ادغام بازارگاهی پیدا نشد. ورود دستی کد رهگیری باید تا تأیید اتصال‌ها باقی بماند.
- **اعلان** می‌تواند ابتدا درون‌برنامه‌ای و پیامکی باشد. وب‌پوش داخلی کاوه‌نگار مستند شده است؛ FCM نیز از نظر فنی وب/اندروید را پوشش می‌دهد، ولی اتکا به زیرساخت گوگل در ایران نیازمند نمونه دسترس‌پذیری و مسیر جایگزین است.

## تفکیک نوع محدودیت

- **فنی:** محدودیتی که مستقیماً در API، مرورگر، شبکه، قالب داده یا چرخه وضعیت وجود دارد.
- **قراردادی/عملیاتی:** قابلیتی که بدون تأیید حساب، قرارداد، احراز هویت، فعال‌سازی ابزار یا توافق سطح خدمت قابل اتکا نیست.
- **نیازمند نمونه یا استعلام:** سند عمومی برای نتیجه قطعی کافی نیست؛ باید حساب آزمایشی، بار واقعی یا پاسخ کتبی ارائه‌دهنده گرفته شود.

## ۱. درگاه و تسویه فروشنده

### زرین‌پال: درگاه مستقل و تسویه مستقیم پذیرنده

زرین‌پال در صفحه رسمی درگاه، احراز هویت، ثبت درخواست درگاه برای دامنه و بررسی مدارک را جزو فرایند فعال‌سازی معرفی می‌کند. صفحه رسمی «تسویه مستقیم» نیز می‌گوید وجه تراکنش‌های روزانه در نخستین سیکل پایای روز بعد به حساب پذیرنده می‌رود و فعال‌سازی پس از ثبت درخواست و بررسی شاپرک انجام می‌شود. این مسیر با حالتی سازگار است که هر فروشنده پذیرنده خودش باشد؛ اما اسناد عمومی بررسی‌شده نحوه ساخت و مدیریت انبوه پذیرندگان مستقل زیر یک پلتفرم را توضیح نمی‌دهند. [درگاه پرداخت زرین‌پال](https://www.zarinpal.com/payment-gateway)؛ [تسویه مستقیم زرین‌پال](https://www.zarinpal.com/features/direct-reconcile)

**محدودیت فنی:** هر درگاه به دامنه/پذیرنده و شناسه اتصال خود وابسته است؛ معماری چندفروشگاهی باید نگهداری امن کلید هر فروشنده، تطبیق تراکنش با سفارش و وبهوک/بازگشت پرداخت را حل کند.

**محدودیت قراردادی:** فعال‌سازی منوط به احراز هویت، مدارک و بررسی شاپرک است. معلوم نیست آیا همه زیردامنه‌های فروشگاه‌ها با یک پذیرنده یا پذیرنده‌های جدا پذیرفته می‌شوند.

**نیازمند نمونه/استعلام:** API یا برنامه شریک برای onboarding انبوه فروشندگان، امکان ساخت پذیرنده روی زیردامنه، مالکیت اینماد/دامنه، مسئول بازپرداخت و برخورد با فروشنده تعلیق‌شده.

### وندار: درگاه، کیف پول و API تسویه

مستندات رسمی وندار API درگاه، کیف پول، تسویه تکی و گروهی را فهرست می‌کنند. در API تسویه تکی، مبلغ، شماره شبا، شناسه یکتای سمت کسب‌وکار و نشانی اعلان وضعیت پذیرفته می‌شود؛ تسویه پیش‌فرض ACH/پایا است و گزینه A2A نیازمند فعال‌کردن ابزار مربوط است. پاسخ شامل وضعیت، زمان تخمینی، رسید و کد مرجع می‌شود. [فهرست مستندات وندار](https://vandarpay.github.io/docs/)؛ [API تسویه وندار](https://vandarpay.github.io/docs/settlement/)

**محدودیت فنی:** مستندات حداقل ۵٬۰۰۰ تومان برای درخواست تسویه تکی ذکر می‌کنند؛ وضعیت‌های بانکی ناهمگام‌اند و باید وبهوک، retry، idempotency، مغایرت و قطعی بانک مدیریت شود. A2A برای همه بانک‌ها همواره در دسترس نیست و API سلامت بانک ارائه شده است.

**محدودیت قراردادی:** داشتن API تسویه به یک شبا به‌تنهایی ثابت نمی‌کند که پلتفرم مجاز است وجوه سفارش خریداران را در کیف پول خود جمع و به فروشندگان ثالث بپردازد. سطح دسترسی APIها و ابزار A2A نیز به حساب کسب‌وکار وابسته است.

**نیازمند نمونه/استعلام:** مجوز تسویه به فروشندگان ثالث، قواعد KYC و تطابق نام صاحب شبا، سقف روزانه/ماهانه، کارمزد، زمان نگهداری وجه، بازگشت تسویه ناموفق و مسئولیت مالیاتی/گزارش‌دهی.

### وندار «میاندو»: نامزد پرداخت محافظت‌شده

مستندات رسمی «معاملات امن» می‌گویند استفاده از ابزار ابتدا باید برای کسب‌وکار درخواست و پس از تأیید فعال شود. API طرفین معامله را با نام، نام خانوادگی، کد ملی، موبایل و تاریخ تولد می‌سازد؛ ایجاد معامله نیز موبایل و شبای خریدار و فروشنده، کالاها، مبلغ و روش پرداخت را می‌خواهد. پس از تأیید طرفین لینک پرداخت صادر می‌شود؛ نهایی‌سازی به معنای تحویل و آزادشدن مبلغ برای فروشنده است و API لغو، ثبت مشکل، تیکت و وبهوک نیز در مستندات آمده است. [مستندات رسمی معاملات امن وندار/میاندو](https://vandarpay.github.io/docs/miando/)

**محدودیت فنی:** جریان عمومی مستندشده تأیید طرفین و داده هویتی کامل می‌خواهد و ممکن است برای خرید سریع شبکه فروشگاهی سنگین باشد. مدل وضعیت و رخدادها باید با سفارش، انجام سفارش و پرونده اختلاف پلتفرم نگاشت شود.

**محدودیت قراردادی:** فعال‌سازی توسط وندار تأیید می‌شود. متن عمومی درباره SLA حل اختلاف، اختیار تصمیم‌گیری پلتفرم، مدت مجاز نگهداری، دسته‌های کالای مجاز، کارمزد و ظرفیت بازارگاه سکوت دارد.

**نیازمند نمونه/استعلام:** فعال بودن فعلی سرویس در تولید، امکان تجربه white-label یا redirect، حذف تأیید تکراری طرفین، API ثبت/مدیریت اختلاف، مدارک قابل قبول، مهلت‌ها، نقش پلتفرم در رأی، تسویه جزئی، مرجوعی جزئی و ظرفیت چندفروشگاهی.

## ۲. پیامک رمز یک‌بارمصرف

### کاوه‌نگار

API رسمی `verify/lookup` برای ارسال کد تأیید با الگوی از پیش تعریف‌شده ارائه شده است. سند می‌گوید این پیام‌ها اولویت بالا دارند و برای شماره‌هایی که پیامک تبلیغاتی را بسته‌اند نیز ارسال می‌شوند. الگو باید تأیید شده باشد و استفاده از متد به سرویس پیشرفته نیاز دارد. API وضعیت تحویل و callback نیز مستند شده است. [مستندات REST و Lookup کاوه‌نگار](https://kavenegar.com/rest.html)

**محدودیت فنی:** توکن و نام الگو قواعد قالب دارند؛ خطاهای نبود اعتبار، تأیید نشدن الگو و کاراکتر نامعتبر باید مدیریت شوند. وضعیت «تحویل‌شده» به معنای اثبات مالکیت شماره نیست و اعتبارسنجی، انقضا، تعداد تلاش و جلوگیری از سوءاستفاده باید در خود پلتفرم باشد.

**محدودیت قراردادی:** الگو نیازمند تأیید و Lookup نیازمند سرویس پیشرفته است.

### IPPanel

مستندات رسمی Edge API از Bearer token/API key، ارسال مبتنی بر Pattern، الگوهای از پیش تأییدشده، گزارش تحویل و VOTP پشتیبانی می‌کنند. [مستندات Edge API](https://ippanelcom.github.io/Edge-Document/docs/)؛ [ارسال پیامک و VOTP](https://ippanelcom.github.io/Edge-Document/docs/send/)؛ [مدیریت Pattern](https://ippanelcom.github.io/Edge-Document/docs/pattern/)

**محدودیت فنی:** همه endpointها API key را نمی‌پذیرند و token ورود ۱۰ ساعت اعتبار دارد؛ سرویس production باید روش احراز مناسب هر endpoint و چرخش کلید را آزمایش کند.

**محدودیت قراردادی:** الگوها پیش از استفاده تأیید می‌شوند؛ شرایط ارسال خدماتی به فهرست سیاه و سقف نرخ در سند عمومی خلاصه نشده است.

### نمونه لازم برای انتخاب OTP

با هر نامزد روی همراه اول، ایرانسل و رایتل، دست‌کم در چند استان و ساعات شلوغ، p50/p95 زمان تحویل، نرخ عدم تحویل، callback، ارسال به شماره دارای منع تبلیغ، محدودسازی نرخ و failover سنجیده شود. قرارداد باید مالکیت داده شماره‌ها، نگهداری لاگ، SLA، اطلاع رخداد و امکان خروجی گرفتن را روشن کند. انتخاب فقط با تعرفه انجام نشود.

## ۳. ورود گوگل

Google Identity Services برای وب، دکمه ورود، One Tap و ورود خودکار را ارائه می‌کند. اعتبار دریافتی یک ID token حاوی شناسه، نام، ایمیل و تصویر است؛ نشست خود پلتفرم را باید backend مدیریت کند. GIS در webview غیرفعال است و دکمه باید با کتابخانه رسمی گوگل ساخته شود. [راهنمای یکپارچه‌سازی Sign in with Google](https://developers.google.com/identity/gsi/web/guides/integrate)؛ [مرجع JavaScript](https://developers.google.com/identity/gsi/web/reference/js-reference)

**محدودیت فنی:** به بارگذاری `accounts.google.com/gsi` و دسترسی کاربر به حساب گوگل وابسته است؛ webview داخل بعضی اپ‌ها پشتیبانی نمی‌شود. ایمیل گوگل جای تأیید شماره موبایل ایرانی را برای سفارش، گفت‌وگو یا پرونده اختلاف نمی‌گیرد.

**محدودیت قراردادی/منطقه‌ای:** صفحه رسمی Google Workspace می‌گوید دسترسی برخی خدمات تجاری در ایران محدود است و استفاده تجاری Workspace ارائه نمی‌شود. این سند درباره GIS حکم اختصاصی نمی‌دهد، اما نشان می‌دهد نباید دسترس‌پذیری یک سرویس تجاری گوگل در ایران را بدون تأیید فرض کرد. [دسترس‌پذیری Google Workspace](https://support.google.com/a/answer/2891389?hl=en)

**نیازمند نمونه/استعلام:** ساخت OAuth client با هویت حقوقی واقعی پروژه، آزمون دکمه و One Tap روی اینترنت ثابت و همراه داخل ایران، Chrome/Safari/Firefox، Android/iOS و مرورگر درون‌برنامه‌ای اینستاگرام. مسیر شماره موبایل و OTP باید مستقل و همیشه در دسترس بماند.

## ۴. ثبت و رهگیری ارسال

### e-Tipax

صفحه رسمی e-Tipax آن را سرویس کسب‌وکارها با ثبت سفارش، چاپ بارکد، برآورد هزینه، کیف پول، مدیریت سفارش و رهگیری آنلاین معرفی می‌کند. همان صفحه برای عقد قرارداد شماره تماس مشخص می‌دهد؛ بنابراین وجود قابلیت فنی روشن است ولی دسترسی API و شرایط تجاری باید قراردادی تأیید شود. [صفحه رسمی e-Tipax](https://tipaxco.com/etipax)

**محدودیت فنی:** مستندات endpointها، webhook وضعیت، sandbox، نرخ درخواست و نگاشت کامل وضعیت‌ها در صفحه عمومی منتشر نشده است.

**محدودیت قراردادی:** حساب تجاری و احتمالاً قرارداد لازم است؛ تعرفه، COD، خسارت، مرجوعی و محدوده جمع‌آوری باید در قرارداد روشن شوند.

### چاپار

وب‌سایت رسمی چاپار API و افزونه را معرفی و عملیات‌هایی مانند ثبت گروهی، لغو جمع‌آوری، دریافت استان/شهر، برآورد قیمت و Tracking را فهرست می‌کند. صفحه خدمات نیز تفاوت مشتری عادی و قراردادی و لزوم قرارداد برای مشتریان صورت‌حسابی را توضیح می‌دهد. [وب‌سایت رسمی چاپار و فهرست قابلیت API](https://www.chaparnet.com/index.html)؛ [شرایط مشتری قراردادی چاپار](https://chaparnet.com/fast-sending.html)

**محدودیت فنی:** سند عمومی قابل اتکایی از schema، webhook، sandbox، auth و نسخه‌بندی API در دسترس این پژوهش نبود.

**محدودیت قراردادی:** API و شرایط صورت‌حسابی باید از فروش/قرارداد دریافت شوند.

### شرکت پست و مسیر پایه نسخه اول

سامانه عمومی رهگیری شرکت پست با کد رهگیری قابل استفاده است، اما سند رسمی عمومی برای API رهگیری/ثبت بازارگاهی در این بررسی پیدا نشد. نبود سند، نبود API سازمانی را ثابت نمی‌کند؛ فقط اجازه نمی‌دهد روی آن برای نسخه اول تعهد فنی بدهیم. تا زمان قرارداد، فروشنده باید بتواند «شرکت حمل + کد رهگیری» را دستی ثبت کند و خریدار وضعیت اعلام‌شده پلتفرم و لینک رهگیری رسمی را ببیند.

### نمونه لازم برای حمل‌ونقل

برای هر نامزد: ثبت سفارش، چاپ لیبل، لغو، قیمت، جمع‌آوری، کد رهگیری، webhook/polling، مرجوعی و خسارت با مرسوله واقعی آزمایش شود. نگاشت وضعیت‌ها باید میان «ثبت‌شده، تحویل به حامل، در مسیر، تحویل‌شده، ناموفق، برگشتی» یکسان‌سازی شود، بدون آنکه پلتفرم وضعیتی مطمئن‌تر از داده حامل نشان دهد.

## ۵. اعلان

### اعلان درون‌برنامه‌ای

این مسیر به ارائه‌دهنده خارجی وابسته نیست: رخدادهای سفارش، گفت‌وگو و پرونده اختلاف در پایگاه داده ثبت و در مرکز اعلان پلتفرم نمایش داده می‌شوند. برای نسخه وب، این باید منبع اصلی و قابل بازبینی اعلان باشد؛ SMS و push فقط کانال رساندن همان رخدادند.

### وب‌پوش کاوه‌نگار

صفحه رسمی کاوه‌نگار سازگاری با PWA، Chrome، Safari، Firefox، Opera و Edge، SDK رویدادمحور و گزارش دریافت/کلیک را اعلام می‌کند. [سرویس وب‌پوش کاوه‌نگار](https://kavenegar.com/services/webpush)

**محدودیت فنی:** دریافت push به اجازه کاربر، پشتیبانی مرورگر و حفظ subscription وابسته است. ادعای پوشش مرورگر باید روی دستگاه‌های واقعی داخل ایران سنجیده شود.

**محدودیت قراردادی:** تعرفه پس از ظرفیت رایگان، نگهداری شناسه دستگاه، SLA و خروج داده باید استعلام شود.

### Firebase Cloud Messaging

FCM راهکار رسمی چندسکویی برای Android، iOS و وب است. وب به HTTPS، service worker، اجازه اعلان و VAPID نیاز دارد؛ سهمیه پیش‌فرض ارسال پروژه و پاسخ 429 نیز مستند شده‌اند. [معرفی FCM](https://firebase.google.com/docs/cloud-messaging)؛ [راه‌اندازی FCM وب](https://firebase.google.com/docs/cloud-messaging/web/get-started)؛ [سهمیه‌ها](https://firebase.google.com/docs/cloud-messaging/throttling-and-quotas)

**محدودیت فنی/منطقه‌ای:** سند FCM ایران را صریحاً تضمین یا منع نمی‌کند. دسترسی console، endpoint ارسال و دریافت روی اپراتورهای ایران باید نمونه شود. چون سرویس به زیرساخت گوگل وابسته است، نباید تنها کانال رخداد حساس سفارش یا اختلاف باشد.

## پرسش‌های مشترک پیش از انتخاب ارائه‌دهنده

1. آیا استفاده مشخص ما به‌عنوان شبکه فروشگاهی چندفروشنده در قرارداد مجاز است؟ پاسخ کتبی لازم است.
2. هر فروشنده باید قرارداد/حساب جدا داشته باشد یا onboarding و KYC زیرمجموعه ارائه می‌شود؟
3. sandbox واقعی، کلید آزمایشی و نمونه webhook در اختیار پروژه قرار می‌گیرد؟
4. سقف نرخ، سقف مبلغ/حجم، SLA، نگهداری داده و زمان اطلاع رخداد چیست؟
5. idempotency، امضای webhook، retry، IP allowlist و روش چرخش کلید چگونه‌اند؟
6. هزینه ثابت، متغیر، حداقل مصرف، هزینه بازگشت/لغو و شرایط تغییر تعرفه چیست؟
7. در قطع سرویس چگونه خروجی داده می‌گیریم و به ارائه‌دهنده جایگزین مهاجرت می‌کنیم؟
8. چه داده‌ای نزد ارائه‌دهنده نگه داشته می‌شود و مسئول پاسخ به درخواست حذف/اصلاح داده کیست؟

## جمع‌بندی قابل استفاده، بدون تصمیم نهایی

| نیاز | گزینه‌های مستند | نتیجه فعلی | گام اثبات |
|---|---|---|---|
| درگاه/تسویه مستقیم | زرین‌پال؛ وندار | فنی ممکن؛ مدل پذیرندگی چندفروشنده نامشخص | مذاکره شریک + sandbox چندفروشنده |
| پرداخت محافظت‌شده | وندار/میاندو | تطابق مفهومی زیاد؛ قرارداد و UX سنگین محتمل | استعلام فعال بودن + اجرای یک معامله و اختلاف آزمایشی |
| OTP | کاوه‌نگار؛ IPPanel | API و الگو مستند | آزمون تحویل چنداپراتوری و failover |
| ورود گوگل | Google Identity Services | فقط گزینه اختیاری؛ دسترس‌پذیری ایران تضمین نشده | نمونه چندشبکه/دستگاه با fallback OTP |
| حمل‌ونقل | e-Tipax؛ چاپار؛ ثبت دستی برای سایر حامل‌ها | API تجاری موجود، سند عمومی ناقص | قرارداد و مرسوله واقعی؛ حفظ ثبت دستی |
| اعلان | درون‌برنامه‌ای؛ SMS؛ وب‌پوش کاوه‌نگار؛ FCM | معماری چندکاناله شدنی | آزمون اجازه/تحویل و عدم اتکای رخداد حساس به یک کانال |

این یافته‌ها نشان می‌دهند ساخت نمونه عملی ممکن است، اما انتخاب ارائه‌دهنده باید پس از دریافت شرایط کتبی و اجرای نمونه‌های بالا انجام شود. به‌خصوص هیچ ادعایی درباره «حفاظت»، «تضمین بازپرداخت» یا زمان قطعی تحویل/تسویه نباید پیش از تثبیت قرارداد و رفتار واقعی سرویس وارد رابط شود.

## محدودیت پژوهش

- فقط صفحات و مستندات رسمی ارائه‌دهندگان استفاده شده‌اند؛ ادعاهای مقایسه‌ای وبلاگ‌ها و فروشندگان ثالث کنار گذاشته شدند.
- برخی مستندات عمومی وندار تاریخ تغییر قدیمی نشان می‌دهند؛ وجود صفحه به معنای فعال بودن تجاری امروز نیست.
- برای API شرکت پست و جزئیات endpointهای تیپاکس/چاپار سند عمومی رسمی کافی پیدا نشد؛ این موارد عمداً «نیازمند استعلام» ثبت شدند.
- دسترسی واقعی Google Identity Services و FCM از شبکه‌های ایران با مرور اسناد قابل اثبات نیست و به نمونه داخل کشور نیاز دارد.
