# ADR-002: مرز ماژول‌ها و قراردادهای کار موازی

- وضعیت: پذیرفته‌شده
- تاریخ: ۱۴۰۵-۰۵-۲۴
- Issue: [تعیین مرز ماژول‌ها و قراردادهای کار موازی](https://github.com/Mahaan-Amr/sevomart/issues/17)
- تکمیل زیرساخت رخداد: [outbox پایدار و Worker قابل‌بازیابی](https://github.com/Mahaan-Amr/sevomart/issues/76)

## زمینه

نسخه اول را دو توسعه‌دهنده در یک modular monolith می‌سازند. مسیر خریدار و فضای کار فروشنده هر دو به قواعد مشترک فروشگاه، کالا، موجودی، سفارش، پرداخت، انجام سفارش، گفت‌وگو و اختلاف وابسته‌اند. تقسیم سیستم به «بخش خریدار» و «بخش فروشنده» منطق مشترک را تکرار می‌کند؛ monolith لایه‌ای با مدل و جدول‌های مشترک نیز برخورد فایل، migration و تصمیم را زیاد می‌کند. در مقابل، microservice از ابتدا هزینه استقرار و عیب‌یابی توزیع‌شده‌ای دارد که برای تیم دو نفره و MVP توجیه نشده است.

مرزها باید مالکیت داده و قرارداد را روشن، کار موازی را قابل کنترل و تست از همان interface مصرف‌کننده را ممکن کنند؛ بدون اینکه توپولوژی استقرار نسخه اول را پیچیده کنند.

## گزینه‌ها

1. **تقسیم بر اساس خریدار و فروشنده:** هم‌راستا با صفحه‌ها، اما همراه با تکرار منطق سفارش، موجودی و اعتماد و ایجاد دو منبع حقیقت.
2. **monolith لایه‌ای با مدل داده مشترک:** شروع ظاهراً سریع‌تر، اما وابستگی گسترده به جدول و مدل‌های مشترک و برخورد مداوم دو شاخه.
3. **modular monolith قابلیت‌محور با مرزهای service-grade:** مالکیت و interface روشن در یک codebase و پایگاه داده مشترک؛ نیازمند انضباط و کنترل خودکار معماری.
4. **microservice از ابتدا:** استقرار و مقیاس مستقل، در برابر database، شبکه، observability و هماهنگی توزیع‌شده‌ای که مسئله فعلی محصول نیست.

## تصمیم

### شکل کلان

گزینه سوم انتخاب شد: **modular monolith با مرزهای service-grade**. ماژول‌ها قرارداد و داده مستقل دارند، اما microservice نیستند:

- یک codebase و چرخه انتشار اصلی باقی می‌ماند؛
- `web`، `api` و `worker` همان topology مصوب ADR-001 را دارند؛
- فراخوانی هم‌زمان میان ماژول‌ها داخل process انجام می‌شود، نه از طریق شبکه؛
- یک PostgreSQL مشترک داریم، اما هر جدول دقیقاً یک مالک ثبت‌شدهٔ دامنه یا زیرساخت دارد؛
- database، container و deployment جدا برای هر ماژول ساخته نمی‌شود.

### نقشه ماژول‌ها

| ماژول              | مالکیت داده و رفتار                                                                |
| ------------------ | ---------------------------------------------------------------------------------- |
| هویت و دسترسی      | ورود، حساب، تأیید موبایل، احراز هویت و مجوزهای سراسری                              |
| فروشگاه            | هویت و وضعیت فروشگاه، شخصی‌سازی، اعضا و سیاست‌های عمومی                            |
| کالا               | قالب کالا، ویژگی، گونه، قیمت و وضعیت انتشار                                        |
| موجودی             | تعداد قابل‌فروش، رزرو و تاریخچه قابل‌ممیزی تغییرات                                 |
| سفارش              | سبد تک‌فروشگاهی، snapshot تجاری، مبلغ و وضعیت سفارش                                |
| پرداخت             | تلاش‌های تسویه مستقیم، شناسه درگاه، callback، تأیید، مغایرت و سابقه بازپرداخت      |
| انجام سفارش        | آماده‌سازی، بسته‌بندی، ارسال، رهگیری و ارسال معکوس                                 |
| گفت‌وگو            | پیام‌های عادی مرتبط با فروشگاه، کالا یا سفارش                                      |
| اختلاف             | پرونده، دلیل، مدرک، پاسخ رسمی، مهلت، توافق و نتیجه پیگیری                          |
| محتوا              | محتوای فروش، تجربه خرید، وضعیت انتشار و ارتباط با کالا                             |
| فیدها و دنبال‌کردن | رابطه دنبال‌کردن، فید دنبال‌شده‌ها، فید کشف، پیشنهادها و projection جست‌وجوی عمومی |
| رسانه              | آپلود، ذخیره، پردازش، کنترل دسترسی فنی و حذف فیزیکی فایل                           |
| اعلان‌ها           | کانال، قالب، ترجیحات، ارسال، retry و نتیجه provider                                |
| گزارش و آمار       | projectionهای تحلیلی خصوصی و آمار عمومی مجاز                                       |

مسیر خریدار و مسیر فروشنده ماژول دامنه نیستند؛ آن‌ها دو ناحیه مستقل در یک برنامه Next.js هستند که interface ماژول‌های بالا را مصرف می‌کنند. هیچ‌کدام implementation دیگری را import نمی‌کند و منطق دامنه داخل React component یا Server Action قرار نمی‌گیرد.

### قواعد مالکیت داده

- هر جدول و migration یک ماژول دامنه یا مالک زیرساخت ثبت‌شده دارد و فقط شاخه‌ای که همان مالکیت را در Issue اعلام کرده می‌تواند آن را تغییر دهد.
- `platform` فقط مالک زیرساخت عمومی تحویل outbox و رسید مصرف است؛ داده و قاعدهٔ دامنه‌ای در جدول‌های آن قرار نمی‌گیرد و schema رخداد همچنان متعلق به ماژول تولیدکننده است.
- خواندن، join یا نوشتن مستقیم جدول ماژول دیگر ممنوع است. ارتباط از interface یا رخداد انجام می‌شود.
- شناسه ماژول دیگر به‌صورت مقدار مرجع نگهداری می‌شود، نه رابطه ORM قابل پیمایش.
- فیدها و گزارش، projectionهای خود را می‌سازند و منبع حقیقت عملیات نیستند.
- یک حساب می‌تواند در آینده عضو چند فروشگاه باشد؛ عضویت متعلق به فروشگاه است و هویت فقط شخص و مجوز سراسری را می‌شناسد. رابط MVP لازم نیست چندفروشگاهی را نمایش دهد.

### قواعد interface و قرارداد

- هر ماژول مالک interface هم‌زمان، schema رخداد، خطا و نسخه قرارداد خود است. OpenAPI عمومی از همین قراردادها ساخته می‌شود.
- بسته مشترک به شناسه‌های تایپ‌شده، پول، زمان، envelope رخداد و قالب خطا محدود است؛ مدل‌هایی مانند `Order` و `Product` مشترک نمی‌شوند.
- افزودن فیلد اختیاری سازگار مجاز است. تغییر ناسازگار نسخه جدید و مسیر سه‌مرحله‌ای «افزودن، مهاجرت مصرف‌کننده، حذف قدیمی» می‌خواهد.
- مصرف‌کننده contract test خود را در برابر interface منتشرشده مالک اجرا می‌کند.
- مالکیت ماژول دائمی و شخصی نیست؛ هر Issue مالک هماهنگی، فایل‌ها، قراردادها و migrationهای قابل تغییر را اعلام می‌کند.

### ارتباط هم‌زمان و رخداد

- اگر ادامه همان کار به پاسخ نیاز دارد، interface هم‌زمان استفاده می‌شود؛ مانند بررسی قیمت، رزرو موجودی و ساخت تلاش پرداخت.
- واقعیتی که ثبت شده و واکنش فوری نمی‌خواهد با رخداد منتشر می‌شود؛ مانند به‌روزرسانی فید، گزارش و اعلان.
- رخداد همراه تراکنش مالک در outbox ثبت و حداقل یک‌بار تحویل می‌شود؛ مصرف‌کننده باید idempotent باشد.
- `platform` اجاره، retry، شکست نهایی و رسید مصرف را اداره می‌کند؛ تولیدکننده مالک رخداد و مصرف‌کننده مالک اثر دامنه‌ای یا projection خود باقی می‌مانند.
- رخداد جای پاسخ ضروری را نمی‌گیرد. شکست مصرف‌کننده تراکنش ثبت‌شده اصلی را rollback نمی‌کند و با retry پیگیری می‌شود.

### جهت وابستگی و نقاط ادغام اصلی

- سفارش قیمت و امکان فروش را از کالا و رزرو را از موجودی می‌خواهد؛ پرداخت فقط برای مبلغ snapshot‌شده سفارش تلاش می‌سازد.
- انجام سفارش پس از رخداد قابل‌اقدام سفارش شروع می‌شود و رویدادهای آماده‌سازی و ارسال را گزارش می‌کند؛ حق تغییر اقلام، مبلغ یا وضعیت پرداخت را ندارد.
- محتوا برای ثبت تجربه خرید، صلاحیت خریدار را از سفارش می‌پرسد.
- اختلاف snapshot لازم را از سفارش، پرداخت و انجام سفارش می‌گیرد، اما داده آن‌ها را تغییر نمی‌دهد.
- فیدها و دنبال‌کردن رخدادهای عمومی فروشگاه، کالا و محتوا را به projection نمایشی تبدیل می‌کند.
- اعلان‌ها و گزارش و آمار مصرف‌کننده رخدادند و هیچ تصمیم دامنه‌ای به projection آن‌ها وابسته نیست.
- ماژول‌های دامنه فقط `MediaId` نگه می‌دارند؛ رسانه کاربرد دامنه‌ای فایل یا وضعیت انتشار را تعیین نمی‌کند.

قواعد اختصاصی این نقاط ادغام عبارت‌اند از:

- گفت‌وگو پیام روزمره است و تاریخچه آن خودکار مدرک رسمی محسوب نمی‌شود؛ کاربر پیام یا فایل مشخص را به پرونده اختلاف متصل می‌کند.
- اختلاف می‌تواند تخلف، توافق و اقدام عملیاتی را ثبت کند، اما در تسویه مستقیم دستور بازپرداخت تضمین‌شده یا تغییر وضعیت پرداخت صادر نمی‌کند.
- تجربه خرید در محتوا فقط پس از تأیید صلاحیت ثبت‌کننده توسط سفارش منتشر می‌شود. توقف انتشار کالا، محتوای گذشته را خودکار حذف نمی‌کند و محتوا بر اساس رخداد دریافتی درباره نمایش تصمیم می‌گیرد.
- فیدها و دنبال‌کردن تبلیغ پولی را از پیشنهاد طبیعی جدا و برچسب‌گذاری می‌کند و حق تغییر فروشگاه، کالا یا محتوا را ندارد.
- ماژول دامنه عمومی یا خصوصی بودن رسانه را تعیین می‌کند و رسانه فقط سیاست دسترسی فنی را اعمال می‌کند.
- هویت و دسترسی مالک رمز یک‌بارمصرف و اعتبار آن است؛ اعلان‌ها فقط پیام را تحویل می‌دهد. شکست اعلان تراکنش اصلی را rollback نمی‌کند.
- گزارش و آمار، بازدید، ذخیره، افزودن به سبد، نرخ تبدیل و رشد فروش را خصوصی نگه می‌دارد. خروجی عمومی فقط دنبال‌کنندگان، کالاهای فعال، خریدهای تأییدشده و امتیاز دارای نمونه کافی است و زمان آخرین به‌روزرسانی را نشان می‌دهد.

### گردش کار چندماژولی

use caseهای چندماژولی در گردش کارهای کوچک و بدون جدول یا منطق دامنه هماهنگ می‌شوند. orchestrator عمومی و همه‌کاره ساخته نمی‌شود.

در ثبت سفارش، گردش کار به‌ترتیب قیمت و امکان فروش را می‌گیرد، موجودی را رزرو می‌کند، سفارش snapshot‌شده را می‌سازد و پس از commit تلاش پرداخت ایجاد می‌کند. رزرو موجودی و ایجاد سفارش می‌توانند در یک transaction داخلی باشند؛ تماس provider خارجی هرگز داخل transaction پایگاه داده انجام نمی‌شود. شکست ساخت تلاش پرداخت، سفارش را در وضعیت «در انتظار پرداخت» قابل retry نگه می‌دارد و رزرو مهلت انقضا دارد.

مرجوعی در MVP ماژول مستقل نیست: فروشگاه مالک سیاست جاری، سفارش مالک snapshot سیاست، اختلاف مالک پرونده و توافق، انجام سفارش مالک ارسال معکوس و پرداخت مالک سابقه بازپرداخت ثبت یا تأییدشده است. تسویه مستقیم اجازه تضمین یا تحمیل بازپرداخت را به پلتفرم نمی‌دهد.

### همکاری و کنترل خودکار

- یک برنامه Next.js و یک design system داریم؛ مسیر خریدار و فروشنده route group، پوشه، تست و مالک تغییر مستقل دارند.
- design system و تنظیمات سراسری در هر لحظه یک مالک دارند و تغییر مشترک پیش از شاخه‌های مصرف‌کننده در PR کوچک ادغام می‌شود.
- architecture test import مستقیم implementation ماژول دیگر، import میان دو مسیر وب و دسترسی خارج از interface را رد می‌کند.
- مالکیت جدول و migration به‌صورت قابل‌بررسی در CI ثبت می‌شود.
- هر ماژول از interface خود با PostgreSQL واقعی integration test می‌شود؛ OpenAPI و رخداد compatibility و contract test دارند.
- گردش کارهای ثبت سفارش، پرداخت ناموفق، انقضای رزرو و مرجوعی آزمون سرتاسری دارند.
- adapterهای درگاه، پیامک و object storage با fake قراردادی آزموده می‌شوند و تست دامنه به provider واقعی وابسته نیست.

### زبان تثبیت‌شده

- یک مورد رسمی «پرونده اختلاف» است و وضعیت آن در مسیر پیگیری سفارش دیده می‌شود.
- نام بخش خریدار «کشف»، اصطلاح محصول «فید کشف» و نام ماژول «فیدها و دنبال‌کردن» است.

## پیامدها

- دو توسعه‌دهنده می‌توانند در مسیرهای خریدار و فروشنده پیش بروند، بدون اینکه منطق مشترک را دو بار بسازند.
- جداسازی مالکیت داده، coupling پایگاه داده و برخورد migration را کم می‌کند؛ در مقابل projection، outbox و contract test کار بیشتری نسبت به monolith لایه‌ای می‌خواهند.
- قابلیت استخراج آینده بهتر می‌شود، اما هیچ ماژولی صرفاً برای استخراج احتمالی به microservice تبدیل نمی‌شود.
- queryهای عمومی و تحلیلی ممکن است با تأخیر کوتاه eventual consistency نمایش داده شوند و باید زمان آخرین به‌روزرسانی را روشن کنند.
- تغییر قابلیت چندماژولی معمولاً به قرارداد کوچک و چند PR مصرف‌کننده نیاز دارد؛ این هزینه آگاهانه برای شفافیت و قابلیت مرور پذیرفته شده است.

## بازنگری

این تصمیم وقتی باز می‌شود که یکی از این شواهد وجود داشته باشد:

- یک ماژول به استقرار یا مقیاس مستقل اندازه‌گیری‌شده نیاز پیدا کند؛
- latency فراخوانی‌های داخل process یا contention پایگاه داده از SLO مصوب عبور کند؛
- یک مرز دائماً به transaction و تغییر schema مشترک نیاز داشته باشد و نشان دهد دو ماژول در واقع یک ماژول عمیق‌ترند؛
- outbox و projection برای نیاز واقعی محصول هزینه عملیاتی نامتناسب بسازند؛
- قواعد حقوقی یا پرداخت، مالکیت داده یا جداسازی عملیاتی تازه‌ای الزام کنند.
